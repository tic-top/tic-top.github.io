Lakehouse 架构（如 Databricks、Apache Iceberg）融合了数据湖的灵活性和数据仓库的查询性能，但也带来了一个新问题：在多种存储格式、分区策略和缓存配置下，同一条 SQL 的执行时间可能天差地别。

本文介绍我在 University of Michigan 研究期间构建的 SQL 执行时间预测模型。

## 问题定义

给定一条 SQL 查询和当前的 Lakehouse 配置（存储格式、分区方式、数据规模、并发度等），预测其执行时间。

这个预测能力的价值在于：
- **查询调度**：优先执行预计耗时短的查询
- **资源分配**：为长查询预留更多计算资源
- **配置推荐**：自动选择最优的存储和分区策略

## 特征工程

我们从三个层面提取特征：

### 查询特征
- SQL 语法树（AST）的结构特征：JOIN 数量、子查询深度、聚合函数类型
- 涉及的表和列统计信息

### 数据特征
- 表的行数和文件数
- 数据格式（Parquet / Delta / Iceberg）
- 分区键和分桶策略

### 系统特征
- 集群规模和节点配置
- 当前并发查询数
- 缓存命中率

## 模型选择

我们对比了几种方案：

| 模型 | MAPE | 推理延迟 |
|------|------|---------|
| Linear Regression | 45.2% | <1ms |
| XGBoost | 23.8% | ~2ms |
| LightGBM | 22.1% | ~2ms |
| Transformer (ours) | **18.6%** | ~15ms |

最终采用了基于 Transformer 的方案，将 SQL 的 AST 序列化后作为输入，结合数据和系统特征进行联合编码。

## 关键洞察

1. **数据格式的影响被低估了**：从 CSV 切换到 Parquet 可以带来 3-10x 的查询加速，这在特征重要性分析中排名第一
2. **分区键选择至关重要**：错误的分区键可能导致全表扫描，比没有分区更慢
3. **并发度是隐藏变量**：同一查询在低并发和高并发时的执行时间差异可达 5x

## 应用

我们将这个预测模型集成到了一个查询优化建议系统中，可以在用户提交 SQL 前给出预估时间和优化建议。在内部测试中，这套系统帮助将平均查询响应时间降低了 30%。
